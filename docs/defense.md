# Сценарий защиты (20 минут)

## 1. Запуск и цепочка HTTP → БД (5 минут)

1. `docker compose up --build -d --wait`.
2. `docker compose logs migrate api`: показать Flyway и JSON API-логи.
3. `docker compose exec api python -m scripts.demo`.
4. Открыть psql, выполнить SELECT из README. Сопоставить напечатанные PRODUCT_ID
   и ORDER_ID со строками products/orders/order_items/user_operations.
5. Открыть Swagger `/docs`; показать contract-first файл и generated-код.

## 2. Альтернативные сценарии (5 минут)

В переданном задании отдельный обещанный раздел E2E-сценариев отсутствует;
проверяются следующие сценарии, выведенные из самих требований:

- `price=0`, `stock=-1`, пустые items, quantity=0/1000: 400 VALIDATION_ERROR,
  `details.fields` содержит поле. Проверить, что новых строк orders нет.
- Неактивный/архивный товар: 409 PRODUCT_INACTIVE; несуществующий UUID: 404.
- quantity выше stock: 409 INSUFFICIENT_STOCK, остаток не меняется.
- Повторный POST заказа: при лимите 1 минута сначала 429 ORDER_LIMIT_EXCEEDED;
  после истечения лимита — 409 ORDER_HAS_ACTIVE.
- Ошибка PUT после возврата старых резервов: исходные остатки и позиции сохранены.
- Промокод с max_uses=1: второй покупатель получает PROMO_CODE_INVALID;
  обновление первого заказа не расходует второй usage.
- Процент 70 даёт скидку до 70%; процент 70.01 или 90 оставляет полную цену.
- После изменения цены каталога PUT сохраняет цену существующей позиции;
  впервые добавляемая позиция получает текущую цену.
- NUL в текстовых полях товара или фильтре category: 400 VALIDATION_ERROR.
- Цена 3 млрд, количество 4 и промокод 50%: итог и скидка по 6 млрд,
  заказ допустим. Переполнение итоговой суммы или скидки вызывает полный откат.
- Сумма ниже min_order_amount: POST даёт 422; PUT снимает старую скидку и usage.
- USER изменяет товар / SELLER изменяет чужой товар: 403 ACCESS_DENIED.
- Чужой заказ: 403 ORDER_OWNERSHIP_VIOLATION; ADMIN получает доступ.
- Повторная отмена: 409; остатки и promo usage не возвращаются второй раз.
- Refresh вместо access: 401; повторное использование старого refresh: 401.
- Для переходов создать ADMIN, выполнить CREATED → PAYMENT_PENDING → PAID,
  затем попытаться отменить или обновить: 409 INVALID_STATE_TRANSITION.
- Конкурентная покупка последних единиц: тест
  `tests/test_orders.py::test_concurrent_reservations_never_oversell`.

## 3. Ключевые места кода (5 минут)

- OpenAPI: отдельные ProductCreate/ProductUpdate/ProductResponse, enum, bounds,
  security, error responses.
- `scripts/generate.py`: DTO из стандартного генератора, корректировка типов и
  точных границ, генерация HTTP-хэндлеров; никаких ручных DTO.
- Миграция: FK, CHECK, partial unique index, idx_products_status, updated_at trigger.
- `orders.create/update/cancel`: проверки в заданном порядке; один connection
  и одна транзакция, rollback при исключении.
- `promos.reapply`: свой usage не считается новым; снятие при неприменимости.
- `auth.refresh`: блокировка refresh row делает ротацию одноразовой даже при гонке.
- Middleware: оборачивает весь HTTP-запрос, возвращает X-Request-Id и пишет JSON.

## 4. Теория (5 минут)

**Зачем контракт до кода?** Он фиксирует пути, типы, ограничения и ошибки.
Модели и HTTP-сигнатуры генерируются из одного источника; тесты проверяют, что
сгенерированные ограничения действительно работают.

**Почему Decimal, а не float?** Десятичные цены и копейки должны считаться точно;
binary float не представляет многие десятичные дроби точно. PostgreSQL NUMERIC
и Python Decimal сохраняют десятичную арифметику; округление задано явно.

**Что даёт транзакция?** Изменения склада, заказа и промокода видны вместе после
COMMIT. Исключение вызывает ROLLBACK, в том числе для уже выполненных UPDATE.

**Почему недостаточно проверить stock перед UPDATE?** Два покупателя могут
одновременно увидеть один остаток. FOR UPDATE удерживает блокировку строки до
конца транзакции, второй запрос проверяет уже обновлённое значение. Единый
порядок блокировок товаров уменьшает риск взаимной блокировки.

**Почему блокируется пользователь?** При первом заказе истории операций ещё нет,
поэтому блокировать последнюю операцию бессмысленно. Существующая строка users
сериализует и первые запросы, а unique partial index дополнительно защищает invariant.

**Что такое partial unique index?** Уникальность user_id применяется только
к строкам CREATED/PAYMENT_PENDING. Завершённые и отменённые заказы не мешают новым.

**Чем access отличается от refresh?** Access короткий и передаётся бизнес-API;
refresh долгий и используется только для выпуска новой пары. Проверяется token_type;
refresh хранится в виде хеша и после ротации больше не принимается.

**JWT шифрует данные?** Нет, payload читается; подпись защищает целостность.
Пароли и чувствительные данные в JWT не помещаются. Поддерживается только HS256,
алгоритм не выбирается из недоверенного входа.

**401 или 403?** 401 — токен отсутствует или невалиден; 403 — пользователь
аутентифицирован, но не имеет роли или не владеет ресурсом.

**Зачем Flyway?** Он применяет версионированные миграции один раз, хранит checksum
и историю в flyway_schema_history. Изменение применённой миграции обнаруживается;
для дальнейших изменений добавляют V2, V3 и т.д.
