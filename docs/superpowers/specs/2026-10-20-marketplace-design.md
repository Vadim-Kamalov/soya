# Marketplace API — проектирование

Источник требований: `marketplace_homework_openapi_crud.md`, пункты 1–10.

Результат — API для защиты домашнего задания, без пользовательского интерфейса.
Python 3.12, FastAPI, Pydantic v2, psycopg 3, PostgreSQL 16, Flyway.
Docker Compose запускает БД, миграции, затем приложение. Контракт OpenAPI 3.0.3
хранится в `src/main/resources/openapi/marketplace.yaml`.

`scripts/generate.py` генерирует DTO стандартным datamodel-code-generator и
типизированные FastAPI-хэндлеры из operationId и параметров контракта.
Результат в `app/generated/` игнорируется git и создаётся при сборке и запуске.
Рукописных DTO нет. Реализации operationId находятся в `app/handlers.py`,
бизнес-логика разделена на auth, products, orders и promos.

Все операции изменения выполняются в транзакциях PostgreSQL. Блокировка строки
пользователя сериализует проверки лимита и активного заказа. Товары блокируются
по UUID в одном порядке; промокод — после товаров. Резервы, позиции, скидки и
журнал операций коммитятся вместе. Частичный unique index дополнительно запрещает
два активных заказа. Денежные расчёты используют Decimal и ROUND_HALF_UP.

Уточнения неоднозначностей задания:

- Ставка выше 70% даёт нулевую скидку и полную цену, согласно буквальной
  формулировке задания. При ставке до 70% скидка ограничивается 70% суммы.
  При округлении предел 70% округляется вниз до копеек, сама скидка — HALF_UP.
- Обновление снимает промокод, если он больше не применим, включая истечение,
  отключение и минимальную сумму; собственное использование не считается новым.
- Повторные product_id в запросе суммируются перед проверкой склада.
- Существующие позиции при PUT сохраняют price_at_order, включая изменение
  количества. Новые товары получают текущую цену каталога; удалённые из заказа
  товары при повторном добавлении считаются новыми.
- Вместимость DECIMAL(12,2) проверяется после скидки для total_amount и
  discount_amount. Промежуточная сумма может превышать этот предел.
- NUL запрещён в текстовых полях товара и фильтре category посредством pattern
  в OpenAPI; generated DTO и HTTP-параметры отклоняют его до бизнес-логики.
- CREATED и PAYMENT_PENDING можно отменить; остальные переходы линейны.
  Дополнительный ADMIN endpoint `POST /orders/{id}/status` позволяет показать
  весь автомат состояний и запрещённые переходы.
- ADMIN обходит проверку владельца заказа; SELLER управляет только своими
  товарами. Публичная регистрация допускает USER и SELLER; ADMIN создаётся CLI.
- Refresh JWT ротируются, их хеши хранятся в БД. Access и refresh различаются
  claim token_type; роль берётся из актуальной записи пользователя.

Валидация тела и параметров задаётся в контракте; единый формат ошибок включает
список полей. JSON middleware логирует каждый запрос и маскирует пароли,
токены и Authorization. X-Request-Id всегда новый UUID.

Проверка: pytest на настоящем PostgreSQL после Flyway, HTTP-запросы через
TestClient, включая конкуренцию, откаты, роли, refresh и ошибки; отдельный E2E
скрипт для запущенной системы и SELECT таблиц для защиты.
